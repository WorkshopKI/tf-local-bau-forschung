Architektur

Eine HTML-Datei, ein Netzlaufwerk, ein zweiter Tab für die KI

Die App läuft komplett im Browser. Der Netzlaufwerk-Ordner ist die Wahrheit, die Browser-Datenbank nur ein schneller Cache. Anträge kommen als nächtlicher CSV-Export aus dem Fachsystem; die interne KI wird über einen zweiten Tab angesprochen.

Kein Server

Deployment = Datei auf den File-Server kopieren. Kein IT-Support, keine Installation, keine Flags.

Share = Wahrheit, IDB = Cache

Ein Varianten-Wechsel startet mit leerer Datenbank und lädt frisch vom Share — es gibt keinen Migrationscode.

Trust-Modell

Alle haben SMB-Schreibrecht; der Schutz ist clientseitig (Kurator-/Rollen-Passwort), Backups schützen gegen Versehen.

Build-Ablauf (scripts/build-with-config.mjs)

  1. Config laden, mit _shared.json deep-mergen, validateConfig
  2. Env setzen: TEAMFLOW_CONFIG, Build-Zeit, Git-Hash
  3. tsc -b && vite build --mode single (vite-plugin-singlefile)
  4. Post-Build-Strip der doppelten WASM-Payloads (Guard: 1–4 Fundstellen)
  5. Kopie nach dist-single/<outputFilename>.html, .bat-Helfer mit CRLF
Sichtbarkeit

Vier Achsen entscheiden, ob ein Feature erscheint

Ein Feature ist sichtbar, wenn alle vier es zulassen: einkompiliert (Flag), freigeschaltet (Zusatzpasswort), gewollt (Beta/Experte-Schalter) und die passende Rolle (Kurator). Abnahme immer mit ausgeschaltetem Beta-Schalter.

Pflege dieser Doku

Wie das Dashboard aktuell bleibt

Die Kennzahlen, der Changelog und der Commit-Stempel werden bei jedem Bau direkt aus dem Repo gemessen (npm run docs:dashboard). Die Abläufe, Texte und das Glossar sind kuratiert und liegen in docs/docu-dashboard/data.json.

Einmal im Monat klont der Claude-Code-Skill docu-dashboard das Repo frisch, vergleicht den Stand mit last-build.json, sichtet die Changelog-Einträge seither auf neue oder geänderte Features, pflegt die betroffenen Abläufe nach und baut die Datei neu. Das Ergebnis ist dieses eine HTML — als Download und als geteilte Seite.
